# CLAUDE.md — SPORTFORCE 3D

Tienda de ropa deportiva con diseñador 3D. **Una sola aplicación de escritorio JavaFX** con base de datos **SQLite local**. Sin servidor.

`PROMPT.md` es el encargo original. Este archivo registra los cambios acordados con el usuario que **tienen prioridad sobre el prompt**:

1. Nombre: **SPORTFORCE 3D** (no SportForge) en interfaz, logotipo, títulos de ventana, instalador, README y paquetes (`com.sportforce3d…`). El monograma sigue siendo "SF". `design/` conserva el nombre antiguo y **no se modifica**; las copias renombradas viven en `src/main/resources`.
2. Base de datos: **SQLite** (`data/sportforce3d.db`), driver xerial `sqlite-jdbc`, migraciones Flyway, `PRAGMA foreign_keys=ON`, montos en **céntimos (INTEGER)**, fechas **ISO-8601 UTC en TEXT**.
3. Arquitectura: una app JavaFX, sin Spring Boot ni API REST. Contraseñas BCrypt. **Roles ADMIN y CLIENTE se verifican en la capa service** (`Session.requireRole`), no solo ocultando botones.
4. Pagos: Yape, Plin y transferencia con **verificación manual del ADMIN**. Tarjeta **deshabilitada con "Próximamente"** (necesitaría un servidor para webhooks).
5. README sin pgAdmin ni Docker; explica dónde se crea el `.db` y cómo reiniciarlo.

## Comandos

```bash
./mvnw verify            # compila y ejecuta las pruebas (Windows: mvnw.cmd verify)
./mvnw javafx:run        # abre la aplicación
./mvnw javafx:run -Djavafx.args=--reset-db   # recrea la BD con datos de prueba
```

- Java 21 (LTS), Maven Wrapper 3.9.16 (no hace falta Maven instalado).
- Punto de entrada: `com.sportforce3d.app.Launcher` (no extiende `Application`, así funciona desde el classpath).
- Argumentos: `--reset-db` (borra y recrea la BD con datos de prueba), `--gallery` (abre la galería de componentes).
- Ruta de la BD: `-Dsportforce.db=…` > variable `SPORTFORCE_DB` > `data/sportforce3d.db` relativo a la carpeta de trabajo.
- Ruta de la BD instalada (lanzador de jpackage, propiedad `jpackage.app-path`): `%APPDATA%\SportForce3D\data\sportforce3d.db`. Registros en `<carpeta del .db>/logs` (Launcher define `sportforce.logdir` antes del primer logger).
- Configuraciones de IntelliJ en `.run/`: Desktop, Desktop (reiniciar BD), Galería de componentes, Desktop (Maven javafx:run), Tests, Capturas 3D, Capturas uniforme de ejemplo (`CaptureTool docs/capturas/etapa4 ETAPA4`), Capturas personas 3D (`CaptureTool docs/capturas/etapa8 PERSONAS`, sin uniforme), Capturas uniformes 3D (`CaptureTool docs/capturas/etapa8 UNIFORMES`, `SampleDesigns.forPerson`), Capturas finales (`tools.ScreenTour`, en src/test), Capturas catálogo realista (`tools.RealisticTour`), Instalador de Windows.
- Prendas simuladas (Etapa 9): `D:\Blender\blender.exe -b --factory-startup -P tools/blender/generar_prendas.py -- --persona hombre|mujer|nino|nina [--vistas carpeta] [--sin-hornear]` (Blender 5.2.2 LTS, 1–4 min por persona). Capturas: **Capturas tela simulada** (`CaptureTool docs/capturas/etapa9 TELA`, las 4 personas).
- Instalador: `powershell -ExecutionPolicy Bypass -File packaging\build-installer.ps1 [-Type exe|msi|app-image] [-SkipTests]`. jpackage del JDK 21 necesita **WiX 3.x** (no 4+); sin WiX genera la carpeta portable. ### Reglas que no se rompen

- **Permisos en service.** Todo método que requiera rol llama `session.requireRole(Role.ADMIN)` **como primera línea** o `session.requireUser()`. `Session.start/end` son package-private: solo `AuthService` abre o cierra sesión. En la app `Session(users::findById)`: `requireRole` relee el usuario de la BD (quitar ADMIN o desactivar tiene efecto inmediato), por eso solo se llama en services, fuera del hilo de la interfaz. `AdminPermissionsTest` recorre por reflexión todos los métodos públicos de los services de administración con una sesión CLIENTE: un service de ADMIN nuevo se agrega ahí.
- **Inicio de sesión:** 5 fallos seguidos → correo bloqueado 5 min, persistido en `login_attempts` (sobrevive a reiniciar). Contraseñas ≤ 72 **bytes** UTF-8 (`Validators.utf8Length`).
- **Validación de entradas:** todo texto libre pasa por longitud + `Validators.plainText` (sin caracteres de control; `multiline` para notas y motivos). En la vista, `Inputs.limit(campo, max)` evita escribir de más.
- **Nada de BD ni BCrypt en el hilo de JavaFX**: usa `Async.run(work, onSuccess, onError)`.
- **Contraseñas** como `char[]`, se limpian tras usarse. Nunca se registran en logs.
- **Errores al usuario** vía `ErrorMessages.of(e)`: sin trazas ni SQL.
- **Montos** siempre `long` en céntimos; formatear solo con `Money.format`.
- **Fechas** `Instant.toString()` (UTC ISO-8601); mostrar en `America/Lima`.
- **No hay botones decorativos**: lo no implementado se deshabilita con texto visible "Próximamente" (`SfButton.comingSoon()`, `SidebarNav.addItem(..., false)`). Los tooltips no aparecen en controles deshabilitados.
- **No simular pagos** ni marcar pedidos como pagados sin verificación de un ADMIN.
- **Sin marcas de terceros** (Puma, Adidas, Nike…). Al subir logos, el cliente declara tener derecho a usarlos (`design_assets.rights_declared = 1`).
- Migraciones: **nunca editar** una migración aplicada; agregar `V4__…sql`, `V5__…sql`.
- **Pedidos**: `OrderService.placeOrder` hace todo en una transacción (correlativo, pedido, líneas con precio congelado, reserva de stock con `quantity - reserved >= n`, historial, pago PENDIENTE, vaciar carrito). Cualquier excepción revierte todo. Cancelar libera `reserved`. Al aprobar un pago (Etapa 5) habrá que convertir la reserva en descuento de `quantity`.
- **Stock** disponible = `inventory.quantity - inventory.reserved`. El ADMIN nunca puede dejar `quantity` por debajo de `reserved`.
- **Envío**: `store_settings.shipping_flat_cents` (S/ 15.00) y `free_shipping_from_cents` (S/ 299.00), vía `CatalogService.shippingFor`.
- **Búsqueda**: `products.search_key` = nombre + descripción + SKU en minúsculas y sin tildes (`Texts.searchKey`). `ProductRepository.save` lo mantiene.
- **3D**: espacio del modelo en metros, Y arriba, +Z frente, +X = izquierda del maniquí. `GridSurface` convierte a JavaFX con una rotación de 180° en X `(x, -y, -z)`. Las prendas se generan sobre `BodyShape` y se desplazan sobre la **normal real** (no radialmente). Bordes enrollados: las filas que miran hacia adentro llevan pista de normal hacia adentro. La geometría se genera en segundo plano (`ModelData` sin objetos de JavaFX) y se convierte a `TriangleMesh` en el hilo de la interfaz. Tras tocar la geometría, ejecutar **Capturas 3D** y revisar `docs/capturas/` antes de dar por bueno un cambio.
- **Diseños** (Etapa 4):
  - `DesignDocument` es la fuente de verdad; la UI nunca lo muta: todo cambio pasa por `DesignerViewModel.edit(label, op, mergeKey)` → `CommandStack`. Cambios continuos (arrastrar, deslizadores, escribir) usan la misma `mergeKey` y `seal()` al soltar: un gesto = un paso de deshacer.
  - Cambiar el formato del JSON: subir `DesignDocument.SCHEMA_VERSION` y convertir los antiguos en `DesignJson.read`; los campos desconocidos se ignoran.
  - Guardar crea una **versión nueva** en `design_versions` y reescribe `design_elements` (ficha técnica normalizada). Capturas frente/espalda en `storage/designs`. Un ADMIN puede abrir (no borrar) diseños de clientes.
  - Logos: PNG/SVG ≤ 5 MB, `rights_declared = 1` obligatorio, dedupe por SHA-256 y solo el dueño puede usarlos. `SvgLoader` rechaza DOCTYPE/entidades externas.
  - Precio: `DesignPricing` — el material de serie de cada ranura (`MaterialSlot.defaultCode`) va incluido; los demás suman `surcharge_cents`. La Etapa 5 debe recalcularlo en el service al agregar al carrito.
  - `TextureComposer` dibuja con **Java2D en CPU** y sube solo el resultado (`WritableImage`, dos por prenda que se alternan). **No usar Canvas de JavaFX para texturas grandes**: cada `clip()` crea una máscara del tamaño del lienzo en la GPU y con 2048 px agotaba el pool de 512 MB de Prism (D3D, gráficos Intel). Medido con `-Dprism.verbose=true`: >521 MB con Canvas, 179 MB con Java2D.
  - El render del diseñador se limita a 30 actualizaciones/s (`AnimationTimer` + `DesignRenderer.changedGarments`).
  - El número del short va cerca del ruedo (u .60, v .70): más arriba la cadera curva la isla UV y el texto se inclina.
  - Tras tocar el compositor, el visor o `SampleDesigns`, ejecutar **Capturas uniforme de ejemplo** y revisar `docs/capturas/etapa4/`.
- **Carrito con diseño y pedidos** (Etapa 5):
  - `cart_items.design_id` apunta al diseño guardado (del mismo usuario); el recargo por unidad sale de `DesignPricing` con la versión actual y se recalcula en `CartService.summary()`. Los materiales del diseño deben estar en `product_materials` del producto. Prendas que el diseñador dibuja: `CartService.DESIGNABLE`.
  - `placeOrder` copia el diseño **antes** de la transacción (JSON de la versión actual + capturas a `storage/orders/`), dentro verifica que el carrito no cambió y congela `design_snapshot_json`, `design_front_path`, `design_back_path`, `design_name`, `design_version`. Si algo falla, borra las copias.
- **Pagos** (`PaymentService`): PENDIENTE → (cliente: código 4–40 + comprobante PNG/JPG/PDF) EN_VERIFICACION y pedido PAGO_EN_VERIFICACION → (ADMIN) APROBADO + PAGADO + `commitStock` (quantity y reserved bajan juntos) **o** RECHAZADO con motivo + pedido PENDIENTE_PAGO + pago PENDIENTE nuevo. Índice único parcial de (método, código) para pagos vigentes. Todo con `UPDATE … WHERE status = …` para evitar dobles aprobaciones.
- **Estados a mano** (`AdminOrderService.nextStates`): PAGADO→EN_PRODUCCION→ENVIADO→ENTREGADO; CANCELADO solo antes del pago y con motivo. PAGADO nunca se fija a mano.
- **Dashboard**: venta = pago APROBADO, por día de Lima con `date(verified_at, '-5 hours')` (Lima no tiene horario de verano). Gráficos con clases `.sf-chart` (serie 0 brand, serie 1 accent discontinua, rejilla line).
- **Resaltado** del elemento elegido: `TextureComposer.setHighlight(id)` dibuja un contorno en el color de foco dentro de la textura. Toda captura (guardar, PNG, pedido) pasa por `DesignerController.cleanCapture` para que no salga.
- **Diseñador realista** (Etapa 7): pestañas "Vista realista" (principal, `view/RealisticDesigner`) y "Vista 3D" (el visor de siempre). La vista realista vive en `DesignDocument.realistic` (`design/RealisticSpec`: modelo de frente, colores por zona, diseño, nombre ≤ 12, número 0–99), se edita con `DesignerViewModel.editRealistic` (deshacer/borrador igual que el 3D) y `DesignRules` la valida. `SCHEMA_VERSION` = 2; `DesignJson.read` convierte los de la versión 1 (`realistic` null → `realisticOrDefault()`). Render en segundo plano, máx. 30/s y una tarea a la vez (gana el último cambio). **Guardar siempre usa las fotos realistas** como capturas de frente y espalda (buzos: solo frente, espalda null). Desde un producto con `model_key` el diseño nuevo arranca con su vista (`CatalogService.realisticLook`). Medias sueltas y zapatillas (`focus`) abren en Vista 3D.
- **Visor ADMIN del uniforme** (Etapa 7): "Vista realista" (dibujada en vivo con la copia del pedido) y "Vista 3D"; la ficha (`TechSheet.realistic`) y el CSV llevan modelo, HEX por zona (en pantalla solo las del modelo), diseño, nombre y número. Diseños sin `realistic` (anteriores) abren solo en 3D, sin selector.
- **Marcas** (Etapa 7): revisados dibujos, emblemas y fotos. La zapatilla de `GarmentArt` tenía tres trazos paralelos (ahora ojales y talón propios) y el diseño "dinámico" tres trazos paralelos iguales (ahora de grosor y ángulo distintos). No volver a dibujar tres franjas paralelas en prendas ni calzado.
- **Tarjetas** (Etapa 7): foto subida por el ADMIN > foto realista (`ProductSummary.look` → `RecolorService.thumbnailAsync`, 520 px) > `GarmentArt`. La tarjeta realista queda vacía hasta que llega la imagen (`ProductCard.setImage`); si falla, vuelve a la ilustración. Tras tocarlas (o el diseñador realista), ejecutar **Capturas catálogo realista** (`tools.RealisticTour [carpeta] [todo|catalogo|disenador]`) y revisar `docs/capturas/etapa7/`.
- **Personas 3D** (Etapa 8): la Vista 3D muestra a la persona de la categoría realista (`DesignerViewModel.personaProperty`, sale de `RealisticSpec.modelKey`; productos sin persona conservan la última) **vestida** con `Viewer3D.setDressedPerson` (`HumanModels.dress`, segundo plano, 0,5–2,5 s la primera vez). Se carga solo al abrir la Vista 3D. `setPerson` (sin ropa) queda para las capturas PERSONAS. Si falta el OBJ o falla la carga, `personFallback` = true y se ve el maniquí procedural con el uniforme (selector MANIQUÍ). Todas las partes con `CullFace.BACK` (con NONE el interior del pelo sale oscuro); el MTL de MakeHuman trae `d 0` y se ignora. Las líneas oscuras del flequillo de la niña son de la geometría del peinado braid01 (no cambian con sangrado ni alfa binario). Tras tocar el visor o los modelos, ejecutar **Capturas personas 3D** y revisar `docs/capturas/etapa8/`.
- **Uniforme sobre la persona** (Etapa 8B, `OutfitFitter` + `ClothOps`): no hay prendas nuevas; se trasladan las del maniquí procedural de su talla (`Persona.fallback()`) con **las mismas UV y caras** (las bastas agregan caras al final), así `TextureComposer`, `DesignRenderer`, relieve, resaltado y arrastre funcionan sin cambios (`getModel()` devuelve el uniforme ajustado). **Prendas base** (cuerpo, mangas, short, medias): cada vértice se ubica por altura proporcional (piso, entrepierna = `SHORTS_CROTCH`, axila, cuello; sobre el cuello escala general), ángulo y holgura respecto del eje de su parte; en el maniquí el radio es **analítico** (`BodyShape`; sus piezas se solapan), en la persona la **envolvente convexa** de la sección (72 rayos: la tela no se mete entre pechos, columna ni glúteos). Cuerpo: caída física bajo el punto más saliente (`drapedTo`), rayos radiales en hombros con tope de altura junto al cuello (mezcla continua), límites de radio/holgura estrictos solo hacia los lados; mezclas entre ejes siempre **radiales** (mezclar posiciones deja hendiduras). Mangas: tubo de sección fija sobre 2 % de la altura bajo la axila (`SLEEVE_TUBE`); la intersección con el cuerpo la resuelve la profundidad (mover capas arruga la manga); solo el extremo escondido en el torso del maniquí se mete bajo el cuerpo. Basta doblada (`hemFold`) en ruedo de camiseta y short. Piel oculta: bajo tela a > 3,5 cm de una abertura, o asomando. Zapatillas: sólido sobre cada pie (pies y punta de medias ocultos). `OutfitFitterTest`: UV/caras, tela fuera de la piel (cuerpo ≥ 99 %, mangas ≥ 95 % contando lo tapado por el cuerpo), sin picos, piel que no asoma (rayos), zapatillas y medidas. ## Sistema de diseño (fuente de verdad: `design/`)

- `css/tokens-dark.css` (predeterminado) y `css/tokens-light.css` (comprobantes/reportes): **looked-up colors** `-sf-bg-000 … -sf-focus`, más `-sf-scrim` y colores de sombra `-sf-shadow-card`, `-sf-glow-brand`, `-sf-glow-accent`. Valores idénticos a `design/tokens.json`.
- `css/components.css` usa solo esos nombres. **Nunca un HEX suelto en el CSS de un componente.** (Excepciones en Java: colores de datos del cliente —swatches, muestras de tela— y el monograma con sus colores fijos de `design/emblemas`).
- Tipografía: en JavaFX cada peso es una familia distinta. Nombres exactos: `"Barlow"`, `"Barlow Medium"`, `"Barlow SemiBold"`, `"Barlow Condensed SemiBold"`, `"Barlow Condensed"` + bold, `"Barlow Condensed ExtraBold"`, `"JetBrains Mono Medium"`. No usar `-fx-font-weight` salvo con "Barlow Condensed" bold.
- Clases de texto: `.display-xl .display-l .heading-m .price .title-s .body .body-s .label-text .code`. **El token `label` se llama `.label-text`** porque `.label` es la clase interna de todos los `Label` de JavaFX.
- JavaFX 21 no tiene letter-spacing, text-transform ni transiciones CSS: mayúsculas en el texto (`SfButton` LG, `SfBadge`, etiquetas de campo lo hacen solos) y animaciones con `component/Motion` (120/200/320 ms, `SPLINE(0.2, 0.8, 0.2, 1)`, respeta "Reducir animaciones").
- Precedencia JavaFX: el CSS de autor **gana a los setters**. Si un componente necesita fijar algo por código (p. ej. `contentDisplay`), no lo declares en el CSS.
- Foco: `:focus-visible` con anillo `-sf-focus` de 2 px separado 2 px (`-fx-border-insets: -4`).
- Un solo botón `ACCENT` por vista.

Componentes (`component/`): `SfButton` (accent/primary/ghost/danger/icon · sm/md/lg), `SfBadge`, `SfLink`, `SfTextField`, `ProductCard` (abre ficha / agrega o "Elegir talla"), `GarmentArt` (silueta de la prenda en su color cuando no hay foto), `FilterChip`, `PageNav`, `ChoiceCards<T>` (opción única con "Próximamente"), `OrderStatusBadge`, `ColorSwatch`, `ColorSwatchGroup`, `GarmentPicker`, `MaterialPicker` + `MaterialSample`, `QuantityStepper`, `StatusTimeline`, `EmptyState`, `Toast`, `ConfirmDialog`, `PromptDialog`, `ModalDialog` (formulario modal con ocupado/error), `SidebarNav`, `Logo`, `AppRoot` (raíz de cada ventana: capas de contenido, diálogos y toasts), `Icons` (Ikonli Feather), `Motion`.
